# 🔒 Enterprise Private GPT

Учебный проект локального корпоративного RAG-ассистента, выполненный в рамках домашнего задания OTUS по теме архитектуры диалоговых систем в LangChain.

Цель проекта — продемонстрировать работу защищённого корпоративного RAG-решения, в котором локальная LLM отвечает на вопросы на основании внутренней базы знаний без использования внешних LLM API при выполнении запросов.

---

## 1. Возможности проекта

Приложение умеет:

- загружать локальные корпоративные документы;
- разбивать документы на текстовые фрагменты;
- создавать embeddings локальной моделью;
- сохранять embeddings в локальной векторной базе ChromaDB;
- выполнять семантический поиск по документам;
- извлекать Top-K наиболее релевантных документов;
- передавать найденный контекст локальной LLM;
- отвечать только на основании корпоративной базы знаний;
- отказываться от ответа, если нужной информации в базе нет;
- показывать источники, использованные при формировании контекста;
- изменять параметр Top-K через пользовательский интерфейс;
- показывать время выполнения запроса.

## 6. Тестовая корпоративная база знаний

Для демонстрации используются синтетические документы, не содержащие реальной конфиденциальной информации.

Каталог:

```text
data/documents
```

Документы:

```text
backup_policy.txt
remote_access_policy.txt
security_policy.txt
```

### backup_policy.txt

Содержит правила резервного копирования, в том числе:

- ежедневное резервное копирование в 02:00;
- хранение резервных копий 30 календарных дней;
- выполнение полной резервной копии каждое воскресенье.

### remote_access_policy.txt

Содержит правила удалённого доступа:

- использование корпоративного VPN;
- обязательная многофакторная аутентификация;
- запрет подключения с общедоступных компьютеров;
- необходимость согласования доступа с руководителем.

### security_policy.txt

Содержит правила информационной безопасности:

- смена корпоративного пароля каждые 47 дней;
- минимальная длина пароля 12 символов;
- запрет передачи пароля другим сотрудникам;
- блокировка учётной записи после трёх последовательных ошибок ввода пароля.

## 7. Chunking

Для разбиения документов используется:

```text
RecursiveCharacterTextSplitter
```

Параметры:

```python
CHUNK_SIZE = 500
CHUNK_OVERLAP = 50
```

Первоначально использовался размер:

```python
CHUNK_SIZE = 300
```

При тестировании оказалось, что для небольших документов часть заголовков выделялась в отдельные малополезные chunks.

После проверки результата размер был увеличен до 500 символов.

Для текущей небольшой тестовой базы каждый документ помещается в один chunk.

Результат ingestion:

```text
Загружено документов: 3
Создано чанков: 3
```

## 15. Правила генерации ответа

LLM получает специальный системный prompt.

Основное правило:

```text
Отвечай на вопрос только на основании предоставленного контекста.
Не используй собственные знания для дополнения ответа.
```

Если в найденном контексте нет ответа, модель должна вернуть:

```text
В корпоративной базе знаний нет информации для ответа на этот вопрос.
```

Это позволяет снизить риск ответа модели из собственных знаний при отсутствии информации в корпоративной базе.


### Тест 2. Вопрос вне корпоративной базы

Top-K:

```text
2
```

Вопрос:

```text
Как приготовить яблочный пирог?
```

Ответ:

```text
В корпоративной базе знаний нет информации для ответа на этот вопрос.
```

```text
security_policy.txt
```

```text

```

Несмотря на то, что ChromaDB всегда возвращает ближайшие документы при заданном Top-K, найденные документы не содержали ответа.

LLM выполнила инструкцию и отказалась использовать собственные знания.

Результат:

```text
PASS
```

Результат:

Данный тест демонстрирует, что ответ формируется на основании корпоративного документа.

## 17. Эксперимент с Top-K

Для вопроса:

```text
Как часто необходимо менять корпоративный пароль?
```

были проверены разные значения Top-K.

### Top-K = 1

Результат:

```text
security_policy.txt
```

Ответ:

```text
Смена пароля корпоративной учетной записи должна проводиться каждые 47 дней.
```

Время:

```text
5.57 сек.
```

В контекст попал только непосредственно релевантный документ.

---

### Top-K = 3

Найденные документы:

```text
security_policy.txt
backup_policy.txt
remote_access_policy.txt
```

Ответ:

```text
Пароль корпоративной учетной записи должен меняться каждые 47 дней.
```

Время:

```text
11.11 сек.
```

Ответ остался правильным, однако в контекст дополнительно были переданы нерелевантные документы.

---

### Вывод по Top-K

Для небольшой и хорошо структурированной тестовой базы значение:

```text
Top-K = 1
```

оказалось достаточным для точных вопросов.

Увеличение Top-K повышает количество передаваемого контекста, но может приводить к добавлению нерелевантных документов.

Для реальной корпоративной базы оптимальное значение Top-K должно подбираться экспериментально на контрольном наборе вопросов.

## 20. Работа в корпоративной сети

В процессе выполнения работы использовалась корпоративная сеть с HTTPS proxy и TLS inspection.

Прямое подключение Ollama к:

```text
registry.ollama.ai
```

не работало и завершалось ошибкой:

```text
TLS handshake timeout
```

При использовании корпоративного HTTPS proxy соединение было установлено.

Для первоначальной загрузки моделей использовался разрешённый корпоративный proxy.

После загрузки моделей inference выполняется локально.

---

## 21. Проблема Hugging Face

Первоначально для embeddings планировалось использовать модель:

```text
sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
```

Через Hugging Face.

Однако в корпоративной сети загрузка завершалась ошибкой:

```text
SSL: CERTIFICATE_VERIFY_FAILED
unable to get local issuer certificate
```

Чтобы не отключать проверку TLS и не усложнять учебный проект настройкой сертификатов, было принято решение использовать локальную embedding-модель:

```text
qwen3-embedding:0.6b
```

через Ollama.

Это позволило сохранить полностью локальную архитектуру inference.
